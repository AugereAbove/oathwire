`ConcurrencyMode=shared-beta` removes only the two function reservations using a CloudFormation condition. Public registration remains disabled. This is an invitation-only application, **not a network-private endpoint**: public ingestion, health and CORS routes still exist, and arbitrary requests can consume metered API/Lambda work before application quotas. The ten-execution regional quota is **not an application-specific spending cap**.

Two queue invocations can run while capacity is available, but SQS maximum concurrency does not reserve two slots. API traffic may occupy all ten slots, causing API throttles and delaying both SQS processing and minute reconciliation. Conversely, asynchronous/scheduled invocations can delay API requests; SQS's limit applies only to that mapping, not the worker's other invocation source. HTTP requests can fail rather than queue. Scheduled invocations can be delayed/retried, and multiple delayed reconciliations may overlap. Conditional leases/transactions protect persisted state from duplicate processing, but they do not guarantee service availability or exact-once delivery.

Long throttling/outages can age messages into the DLQ or beyond history retention. Recovery is conditional on restored capacity and retained records; operators must inspect DLQ, queue age, both functions' `Throttles`, `ConcurrentExecutions`, errors and delivery history. Do not claim guaranteed recovery from unlimited starvation. Existing alarms remain; no additional paid alarm/metric/service was added. Start with a few invited testers, no unrelated regional Lambda workloads and no load test. Stop publishing and investigate when throttles persist or queue age rises. Do not respond by removing request, retry or database limits.

The fallback is practical for a controlled demonstration when quota approval is unavailable. Prefer the reserved configuration for ongoing availability and isolation. A quota increase while running shared-beta requires review and migration to reserved mode; preflight deliberately rejects a shared pool larger than ten. The checks are admission checks, not continuous enforcement against later administrator/account changes.

`infra/bootstrap.yaml` has four resources: encrypted private artifact bucket (TLS-only, incomplete multipart cleanup), its bucket policy, a named runtime boundary, and named CloudFormation execution role. The application still expands to 35 resources in either mode. Explicit function/role/frontend-bucket names enable narrower policies; these naming changes must not be blindly applied to an existing deployment because they may replace resources. There is currently no application stack to replace.

Corrections made during review:

- Runtime role management and Lambda PassRole now target exactly the two named application roles. Creation requires the exact runtime boundary. The CloudFormation role cannot edit its own role/policy or create users/access keys, attach arbitrary managed policies, remove runtime boundaries or alter unrelated roles. Unneeded runtime trust-policy updates were removed.
- Frontend bucket management targets the exact account/region-qualified frontend bucket; artifact access is read-only on the application prefix. The runtime boundary retains only the necessary DynamoDB, SQS and log-stream actions.
- Event mapping create/update/delete/read are constrained to the application worker where the API exposes `lambda:FunctionArn`; mapping tag metadata uses the generated-ID resource scope. SQS mapping limit stays 2.
- Cognito mutation and distribution management use the stack ownership tag. API creation uses its regional collection ARN, while mutations of generated API resources require the stack tag. Initial API tagging can address previously untagged APIs because CloudFormation imports before tagging; it cannot retag a resource carrying another stack value. Cognito/CloudFront initial tagging grants require the requested ownership tag and reject a conflicting existing ownership tag. They remain privileged: an untagged unrelated resource could be labeled as this stack if misused. CloudFront needs an initial-tag grant before a new distribution has resource tags. Review the template and execution-role access accordingly.
- CloudFront origin controls/response policies have generated, untaggable IDs. Their management remains scoped to resource type and owning account. Creation APIs without ARN-level support use `Resource: "*"` for only the enumerated actions. These are documented residual scopes, not claims of complete resource isolation.
